1.0 Kubernetes-Cluster auf Hetzner Cloud INF001

Die Plattform muss auf einem Kubernetes-Cluster (k3s) bei Hetzner Cloud betrieben werden. Das Cluster wird mit dem CLI-Tool hetzner-k3s provisioniert. Konfiguration: 1 Controller (CPX22, 2 vCPU, 4 GB) + 2 Worker Nodes (CPX22, 2 vCPU, 4 GB), CNI Flannel, Hetzner CSI für Storage.

Parent links: STK007 Cloud-Native Deployment

Child links: OPS002 Disaster-Recovery-Plan

2.0 GitOps-Deployment mit Flux INF002

Alle Kubernetes-Ressourcen muessen deklarativ in Git verwaltet und durch Flux automatisch auf den Cluster synchronisiert werden. Manuelle kubectl-Änderungen sind im Produktivbetrieb nicht erlaubt. Flux beobachtet das App-Repository (Pfad infra/k8s/) und das IaC-Repository mit einem Poll-Intervall von 10 Minuten.

Parent links: STK007 Cloud-Native Deployment

Child links: OPS001 Rollback-Verfahren dokumentiert und getestet

3.0 TLS-Terminierung mit cert-manager und Let's Encrypt INF003

Alle externen Endpunkte muessen ueber HTTPS mit gueltigem TLS-Zertifikat erreichbar sein. Zertifikate werden automatisch ueber cert-manager und Let's Encrypt (ACME HTTP-01) bereitgestellt und vor Ablauf erneuert. HTTP-Anfragen werden permanent auf HTTPS umgeleitet (301).

Parent links: STK007 Cloud-Native Deployment

4.0 Secrets-Management mit SOPS und age INF004

Secrets (Passwörter, API-Keys, OAuth-Credentials) muessen mit SOPS und age verschluesselt im Git-Repository gespeichert werden. Nur die data/stringData-Felder der Secret-Manifeste werden verschluesselt. Flux entschluesselt sie automatisch beim Deployment. Der private age-Schluessel liegt ausschliesslich als Secret im Cluster.

Parent links: STK016 Sichere Verwaltung von Secrets im Cluster

5.0 PostgreSQL HA via CloudNativePG INF005

PostgreSQL muss ueber den CloudNativePG Operator als Kubernetes Custom Resource betrieben werden. Die Konfiguration umfasst mindestens 2 Instanzen (Primary + Replica) mit automatischem Failover. Der Operator verwaltet den gesamten Lifecycle (Provisioning, Failover, Scaling, Credential-Rotation).

Parent links: STK007 Cloud-Native Deployment

6.0 Service Mesh mit Linkerd (mTLS) INF006

Alle Pod-zu-Pod-Verbindungen innerhalb des Clusters muessen durch Linkerd mTLS verschluesselt werden. Jeder Pod in meshed Namespaces erhaelt automatisch einen Sidecar-Proxy. Die Zertifikats-Hierarchie umfasst Trust Anchor (10 Jahre), Identity Issuer (1 Jahr, cert-manager-rotiert) und Workload Certificates (24h, automatisch).

Parent links: STK007 Cloud-Native Deployment

7.0 Network Policies (Default Deny) INF007

Alle Namespaces muessen eine Default-Deny NetworkPolicy verwenden. Nur explizit erlaubte Verbindungen sind zugelassen. Erlaubte Pfade werden ueber dedizierte Ingress- und Egress-NetworkPolicies definiert. Zusaetzlich werden Linkerd AuthorizationPolicies fuer Service-Level-Zugriffskontrolle eingesetzt.

Parent links: STK007 Cloud-Native Deployment

8.0 Versionierte Image-Tags und automatische Manifest-Updates INF008

Container-Images muessen mit eindeutigen, versionierten Tags (Commit-SHA oder Semver) versehen werden. Die CI-Pipeline aktualisiert nach erfolgreichem Build automatisch den Image-Tag im Deployment-Manifest und committet die Aenderung. Flux erkennt den neuen Commit und loest ein Rolling Update aus. Der Tag latest darf nicht fuer Produktiv-Deployments verwendet werden.

Parent links: STK007 Cloud-Native Deployment

9.0 Backup-Strategie fuer PostgreSQL INF009

Die PostgreSQL-Datenbank muss regelmaessig gesichert werden. Zielwerte: RPO (Recovery Point Objective) < 1 Stunde durch WAL-Streaming, RTO (Recovery Time Objective) < 15 Minuten durch Restore aus Backup. Backups werden auf S3-kompatiblem Storage (Garage auf Netcup VM) gespeichert. Retention: 30 Tage. Regelmäßige Restore-Tests muessen durchgefuehrt werden.

Parent links: STK007 Cloud-Native Deployment

Child links: OPS002 Disaster-Recovery-Plan

10 Monitoring-Infrastruktur INF010

Die Plattform muss ueber einen vollstaendigen Observability-Stack verfuegen: Prometheus (Metriken), Grafana (Dashboards), Loki (Log-Aggregation) und Tempo (Distributed Tracing). Alerting muss bei kritischen Zustaenden (Service down, hohe Fehlerrate, Disk voll) automatisch ausgeloest werden.

11 Traefik HTTPS-Redirect für alle Nicht-ACME-Requests INF011

Ein Traefik IngressRoute auf dem web-Entrypoint (HTTP, Port 80) leitet alle eingehenden Requests per 301 Permanent Redirect auf HTTPS um. Die Route muss eine niedrige Priorität haben, damit die von cert-manager automatisch erstellten ACME HTTP-01 Challenge-Ingress-Ressourcen (Pfad /.well-known/acme-challenge/) Vorrang erhalten und unverschlüsselt erreichbar bleiben.

Parent links: STK035 HTTPS-Umleitung für alle Requests außer Let's Encrypt

12 Traefik Default-Redirect für unbekannte Domains INF012

Ein Traefik IngressRoute auf dem websecure-Entrypoint (HTTPS, Port 443) fängt alle Requests ab, die keiner konfigurierten Domain zugeordnet sind, und leitet sie per 302 Redirect auf https://blog.tomirgang.de um. Die Route muss eine niedrigere Priorität als alle service-spezifischen IngressRoutes haben, damit bekannte Domains korrekt geroutet werden.

Parent links: STK036 Umleitung unbekannter Domains auf Hauptdomain

13 Deklarative Datenbankverwaltung mit CloudNativePG Database CRD INF013

Alle Service-Datenbanken muessen als eigenstaendige CloudNativePG Database Custom Resources (CRD) verwaltet werden (ab CNPG >= 1.25). Jede Datenbank wird als separates Kubernetes-Manifest in infra/k8s/postgres/ definiert. Der Operator reconciliert den Zustand und meldet Fehler im .status-Feld. Die databaseReclaimPolicy muss auf retain gesetzt sein, um versehentlichen Datenverlust zu verhindern. Die bisherige Loesung ueber postInitApplicationSQL wird durch die Database CRD abgeloest.

Parent links: STK007 Cloud-Native Deployment

14 Redis Deployment auf Kubernetes INF014

Redis muss als Single-Instance Deployment im Namespace redis auf Kubernetes betrieben werden. Das Deployment umfasst: Deployment mit Security Context (non-root, read-only Filesystem), ClusterIP Service auf Port 6379, Network Policy die Ingress nur aus dem tomsblog Namespace erlaubt, Passwort-Authentifizierung über Kubernetes Secret. Die Kustomize-Manifeste liegen in infra/k8s/redis/. Redis wird ohne Persistenz betrieben (keine RDB/AOF-Snapshots).

Parent links: STK045 Horizontale Skalierbarkeit und unterbrechungsfreie Updates

15 Kafka-Cluster auf Kubernetes (Strimzi Operator) INF015

Apache Kafka muss als Single-Node-Cluster im KRaft-Modus auf Kubernetes betrieben werden. Die Installation erfolgt über den Strimzi Operator (Helm Chart via Flux HelmRelease, ADR-0026). Der Cluster umfasst: einen kombinierten Controller/Broker-Node (KRaft, kein ZooKeeper), Kafka-Version 3.9.0 passend zur lokalen Entwicklungsumgebung, Ressourcenlimits (512Mi/1Gi Memory, 250m/1000m CPU), persistenten Storage (5Gi, hcloud-volumes), 7 Tage Log-Retention für Event-Replay (SWA-005). KafkaTopic-CRDs werden für die drei initialen Event-Typen angelegt: post.created, post.updated, post.published (je 3 Partitionen, Replication-Faktor 1). Der Kafka-Namespace erhält eine Default-Deny-Ingress-NetworkPolicy mit Ausnahme für den tomsblog-Namespace auf Port 9092. Die Kustomize-Manifeste liegen in infra/k8s/kafka/.

Parent links: STK038 Asynchrone Service-Kommunikation via Kafka oder RabbitMQ

16 RabbitMQ-Cluster auf Kubernetes (RabbitMQ Cluster Operator) INF016

RabbitMQ muss als Single-Node-Cluster auf Kubernetes betrieben werden. Die Installation erfolgt über den RabbitMQ Cluster Operator (Bitnami Helm Chart via Flux HelmRelease, ADR-0026). Der Cluster umfasst: ein RabbitmqCluster-Replikat mit Management- und Prometheus-Plugin, RabbitMQ 4.x (management-alpine) passend zur lokalen Entwicklungsumgebung, Ressourcenlimits (256Mi/512Mi Memory, 100m/500m CPU), persistenten Storage (2Gi, hcloud-volumes), Default-VHost "tomsblog" für Konsistenz mit Docker Compose. Quorum Queues sichern Durability (SWA-014). Der RabbitMQ-Namespace erhält eine Default-Deny-Ingress-NetworkPolicy mit Ausnahme für den tomsblog-Namespace auf Port 5672 (AMQP) und 15672 (Management). Die Kustomize-Manifeste liegen in infra/k8s/rabbitmq/.

Parent links: STK038 Asynchrone Service-Kommunikation via Kafka oder RabbitMQ
