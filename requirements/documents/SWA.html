1.0 Hexagonale Architektur pro Service SWA001

Jeder Microservice folgt der hexagonalen Architektur mit den Schichten: domain/ (reine Fachlogik, keine Framework-Abhängigkeiten), application/ (Ports, Use Cases), adapter/inbound (REST Controller, Event Listener), adapter/outbound (JPA Repositories, Kafka Producer, HTTP Clients).

2.0 Shared Kernel als Framework-freie Library SWA002

Gemeinsame Domain Primitives (EntityId, TenantId, AuthorId, AggregateRoot, DomainEvent, Auditable) werden in libs/shared-kernel bereitgestellt. Diese Library darf keine Spring- oder Framework-Abhängigkeiten haben.

Parent links: SWR001 Post CRUD API, SWR003 Tenant-Isolation auf Datenebene

Child links: IMP006 Shared Kernel Domain Primitives, IMP012 AuthorId im Shared Kernel

3.0 Event-Contracts als geteilte Library SWA003

Alle Cross-Service Events (PostCreatedEvent, PostUpdatedEvent, PostPublishedEvent) und die gemeinsame EventMetadata werden in libs/event-contracts definiert. Consumer und Producer verwenden dieselben Event-Klassen.

Der Blog Content Service wird als Spring Boot 3.x Applikation mit Spring Web (REST), Spring Data JPA (PostgreSQL) und Thymeleaf (SSR UI) implementiert.

5.0 Kafka als Event-Broker SWA005

Apache Kafka (KRaft Mode) dient als Event-Broker für Domain Events (Event Sourcing, Audit-Trail, Replay). Topics werden pro Event-Typ angelegt. Consumer Groups ermöglichen unabhängige Verarbeitung. Kafka ist zuständig für: Event-Streaming, Log Aggregation, Stream Processing, Datenpipelines und Replay-Szenarien. Für Task-Queues und Job-Verteilung wird stattdessen RabbitMQ verwendet (SWA-014).

Parent links: SWR008 RSS/Atom Feed-Generierung, SWR009 Domain Events via Kafka

Child links: IMP005 LoggingEventPublisher (Interim Event Adapter)

6.0 AI Service als separater Adapter SWA006

Die KI-Integration (OpenRouter) wird als Outbound-Adapter im Blog Content Service implementiert. Bei Ausfall liefert der Adapter einen definierten Fehler; die restliche Funktionalität bleibt unberührt (Circuit Breaker Pattern).

Parent links: SWR004 Übersetzung per KI (Author-getriggert), SWR014 Graceful Degradation bei KI-Ausfall

7.0 Domain-Modell mit Aggregates, Entities und Value Objects SWA007

Das Domain-Modell des Blog Content Service besteht aus folgenden Bausteinen:

  • Post (Aggregate Root): PostId, TenantId, AuthorId (Referenz), title, slug, content, status, locale, tags (Set), sources (List), attachments (List)
  • Tag (Entity): TagId, TenantId, name, slug
  • Translation (Aggregate Root): TranslationId, PostId, TenantId, locale, title, content, status, source
  • Source (Value Object): url, title
  • Attachment (Value Object): AttachmentId, filename, contentType, size, show, storageKey
  • AuthorId liegt im shared-kernel als reine Referenz (keine Author-Entity im blog-content)
    • Alle Aggregates und Entities tragen eine TenantId fuer Multi-Tenant-Isolation. Attachments mit show=true werden im Blog-Rendering angezeigt, mit show=false fuer eingebettete Inhalte.

Parent links: SWR001 Post CRUD API, SWR003 Tenant-Isolation auf Datenebene, SWR012 Quellen-Verwaltung

Child links: IMP001 Post Aggregate Root, IMP008 Tag Entity mit Identity, IMP010 Source Value Object, IMP011 Attachment Value Object mit show-Flag, IMP013 TagService und TagUseCase

8.0 Translation als separates Aggregate mit eigenem Lifecycle SWA008

Uebersetzungen werden als eigenes Aggregate modelliert (nicht als Child im Post). Der Lifecycle ist: DRAFT -> REVIEW_PENDING -> APPROVED oder REJECTED. AI-generierte Uebersetzungen starten in REVIEW_PENDING (Autor muss pruefen). Manuelle Uebersetzungen starten in DRAFT. Bei Aenderung einer approbierten Uebersetzung wechselt der Status auf REVIEW_PENDING.

Parent links: SWR004 Übersetzung per KI (Author-getriggert), SWR005 Manuelle Übersetzung

Child links: IMP009 Translation Aggregate, IMP016 TranslationService und TranslationUseCase

9.0 gRPC für synchrone Service-Kommunikation SWA009

Für synchrone Kommunikation zwischen Microservices wird gRPC verwendet. Kafka bleibt für asynchrone, event-basierte Kommunikation zuständig. gRPC bietet typsichere Contracts via Protobuf, effizientes Binary-Protokoll und native Streaming-Unterstützung. Service-Interfaces werden als .proto-Dateien in einer geteilten Library definiert.

Parent links: SWR009 Domain Events via Kafka

10 Authentik OIDC und leichtgewichtiger User-Management-Service SWA010

Die Authentifizierung erfolgt über Authentik (https://auth.do9ita.de) als externem OIDC Provider (ADR-0027). Ein leichtgewichtiger interner User-Management-Service verwaltet plattformspezifische Benutzerprofile, Rollen (ADMIN, AUTHOR, READER) und Tenant-Zuordnungen. Services mit Web-UI agieren als OAuth2 Client (Spring Security OAuth2 Login). API-Endpunkte werden als OAuth2 Resource Server geschützt. Der User-Management-Service synchronisiert Benutzerdaten aus dem OIDC ID Token und stellt eine REST-API für Profil- und Rollenabfragen bereit.

Parent links: SWR007 Rollenbasierte Zugriffskontrolle, SWR016 OIDC Login mit Authentik als externem Provider

11 Domain-basierte Tenant-Resolution am Ingress SWA011

Die Tenant-Auflösung erfolgt am Ingress-Level über den Host-Header. Ein Tenant-Resolution-Service mappt Domains auf TenantIds. Ein Tenant kann mehrere Domains besitzen (Custom-Domain + Plattform-Subdomain). Die aufgelöste TenantId wird als Header (X-Tenant-Id) an nachgelagerte Services propagiert.

Parent links: SWR003 Tenant-Isolation auf Datenebene, SWR017 Domain-basierte Tenant-Auswahl

12 LLM-basierte Kommentar-Moderation als Adapter SWA012

Die automatisierte Kommentar-Überprüfung wird als Outbound-Adapter im Kommentar-Service implementiert. Der Adapter nutzt das OpenRouter-Backend (analog zum AI-Adapter im Blog Content Service, SWA-006). Das Moderation-Interface ist als Port definiert, sodass der LLM-Adapter austauschbar bleibt (z.B. durch regelbasierte Moderation als Fallback).

Parent links: SWR018 Automatisierte Kommentar-Moderation via LLM

13 Flyway für versionierte Datenbank-Migrationen SWA013

Alle Datenbank-Schema-Änderungen werden über Flyway-Migrationen verwaltet. Migrationsdateien liegen unter src/main/resources/db/migration/ mit dem Benennungsschema V{nummer}__{beschreibung}.sql. Hibernate ddl-auto ist auf validate gesetzt (nur Validierung, keine Änderung). Flyway wird beim Service-Start automatisch ausgeführt.

Parent links: SWR001 Post CRUD API, SWR020 Tag CRUD API, SWR021 Translation CRUD API

Child links: IMP015 JpaTagRepository (Outbound Adapter), IMP018 JpaTranslationRepository (Outbound Adapter), IMP019 Flyway Migrationen für Blog Content Service

14 RabbitMQ als Task-Queue-Broker SWA014

RabbitMQ dient als Broker für Task-Queues und Job-Verteilung. Einsatzgebiete: Übersetzungsaufträge, TTS-Generierung, Snapshot- Erstellung, Benachrichtigungen, Request/Reply-Patterns und klassische Service-zu-Service-Kommunikation mit komplexem Routing. Quorum Queues sichern Durability. Dead-Letter-Exchanges behandeln fehlgeschlagene Nachrichten. Die Abgrenzung zu Kafka (SWA-005) folgt ADR-0018: Kafka für Event-Streaming, RabbitMQ für Task-Queues.

Parent links: SWR009 Domain Events via Kafka

15 Database per Service SWA015

Jeder Microservice besitzt seine eigene, dedizierte Datenbank-Instanz. Die Technologiewahl (PostgreSQL oder MongoDB) wird pro Service entschieden. Auch wenn mehrere Services PostgreSQL verwenden, erhaelt jeder eine eigene Instanz. Kein Service darf direkt auf die Datenbank eines anderen Services zugreifen. Service-uebergreifender Datenzugriff erfolgt ausschliesslich ueber gRPC (SWA-009) oder Domain Events (SWA-005).

Parent links: SWR001 Post CRUD API, SWR003 Tenant-Isolation auf Datenebene

16 springdoc-openapi für API-Dokumentation SWA016

Die API-Dokumentation wird mit springdoc-openapi (v2.x) automatisch aus dem Code generiert. springdoc-openapi-starter-webmvc-ui stellt sowohl die OpenAPI-Spezifikation als auch das Swagger UI bereit. Die Annotationen @Operation, @ApiResponse und @Tag aus io.swagger.v3.oas.annotations werden an den REST-Controllern verwendet. Ein globaler OperationCustomizer fügt den X-Tenant-Id Header automatisch zu allen Operationen hinzu. Die Version wird zentral im Parent POM verwaltet.

Parent links: SWR024 OpenAPI/Swagger API-Dokumentation

17 Kubernetes-Cluster-Provisionierung mit hetzner-k3s SWA017

Das Kubernetes-Cluster wird mit dem CLI-Tool hetzner-k3s auf Hetzner Cloud provisioniert. Konfiguration: 1 Controller (CPX22, 2 vCPU, 4 GB), 2 Worker-Nodes (CPX22, 2 vCPU, 4 GB), Standort Nuernberg (nbg1). CNI: Flannel (k3s-Standard). Hetzner CSI (hcloud-volumes) und CCM sind integriert. Updates erfolgen manuell via hetzner-k3s upgrade. Die Cluster-Provisionierung liegt in einem separaten Repository (kubernetes-playground/k3s/), getrennt von den applikationsspezifischen Kubernetes-Ressourcen.

Parent links: SWR010 Container-Image und Health-Checks

18 PostgreSQL-Betrieb mit CloudNativePG Operator SWA018

PostgreSQL wird ueber den CloudNativePG Operator als Kubernetes Custom Resource verwaltet. Der Operator wird als Plattform-Voraussetzung im IaC-Repository installiert. Die konkreten Cluster-Definitionen (Instanz-Anzahl, Sizing, Storage) liegen applikationsspezifisch im tomsblog-Repository unter infra/k8s/postgres/. Initiale Konfiguration: 1 Instanz, 10 Gi Storage (hcloud-volumes), 256 MB shared_buffers, 512 Mi bis 1 Gi RAM. Spaeter wird auf HA (2+ Instanzen) und S3-Backup erweitert.

Parent links: SWR010 Container-Image und Health-Checks

19 Cross-Namespace Secret-Synchronisation mit Reflector SWA019

Cross-Namespace Secret-Synchronisation wird ueber Reflector (emberstack) realisiert. Operator-generierte Secrets (z.B. CloudNativePG postgres-cluster-app) werden per Annotation automatisch in die Ziel-Namespaces der konsumierenden Services gespiegelt. Die Synchronisation erfolgt bei jeder Aenderung am Quell-Secret (einschliesslich Credential-Rotation). Reflector wird als Flux HelmRelease im IaC-Repository installiert und laeuft im flux-system Namespace mit minimalen Ressourcen (64Mi-128Mi RAM).

Parent links: SWR031 Secrets verschlüsselt im Repository und automatisch synchronisiert

20 SOPS+age Verschlüsselung für Secrets im Git-Repository SWA020

Applikationsspezifische Secrets (Admin-Passwörter, API-Keys) werden mit SOPS (Mozilla) und age-Verschlüsselung im Git-Repository gespeichert. Nur die data/stringData-Felder der Kubernetes Secret-Manifeste werden verschlüsselt, Metadaten bleiben lesbar für Code-Reviews. Die Datei .sops.yaml definiert Creation Rules mit Pfad-Pattern und age Public Key. Der Flux kustomize-controller entschlüsselt die Secrets automatisch beim Apply über den Decryption Provider (sops) mit dem age Private Key aus dem sops-age Secret im flux-system Namespace.

Parent links: SWR031 Secrets verschlüsselt im Repository und automatisch synchronisiert

21 TLS-Terminierung am Ingress mit cert-manager und Let's Encrypt SWA021

Die TLS-Terminierung für externen Traffic erfolgt am Traefik Ingress-Controller (k3s-Standard). Zertifikate werden automatisch über cert-manager mit einem Let's Encrypt ClusterIssuer (HTTP-01 Challenge) bereitgestellt.

Architektur:

  • cert-manager wird als Cluster-Operator im IaC-Repository installiert
    • (analog zu CloudNativePG und Reflector).
  • Ein ClusterIssuer (letsencrypt-prod) konfiguriert den ACME HTTP-01 Solver
    • mit Traefik als Ingress-Class.
  • Kubernetes Ingress-Ressourcen referenzieren den ClusterIssuer via Annotation
    • und erhalten automatisch TLS-Zertifikate.
  • HTTP-zu-HTTPS-Redirect wird am Ingress konfiguriert.

Voraussetzungen:

  • cert-manager CRDs und Controller im Cluster (IaC-Repository)
  • DNS A-Record zeigt auf den Hetzner Load Balancer
  • Port 80 am LB offen für ACME HTTP-01 Challenge-Validierung

Parent links: SWR032 HTTPS-Verschlüsselung für externe Zugriffe

22 Linkerd Service Mesh Deployment via Flux und cert-manager SWA022

Linkerd wird als Service Mesh im Kubernetes-Cluster installiert und ueber Flux GitOps verwaltet. Die Installation besteht aus zwei Helm Charts (linkerd-crds und linkerd-control-plane), die als HelmRelease Custom Resources im tomsblog-Repository definiert sind.

Certificate-Management:

  • Ein self-signed ClusterIssuer erzeugt den Trust Anchor (Root CA, 10 Jahre).
  • Ein CA Issuer basierend auf dem Trust Anchor signiert den Identity Issuer
    • (48h Gueltigkeit, automatische Rotation durch cert-manager).
  • Der Linkerd Identity Controller verwendet das Identity Issuer Certificate
    • fuer die Ausstellung von Proxy-Zertifikaten.

Mesh-Injection:

  • Namespaces erhalten die Annotation linkerd.io/inject: enabled.
  • Pods werden beim naechsten Rollout automatisch mit dem Linkerd Sidecar-Proxy
    • versehen.
  • Der tomsblog-Namespace ist mit der Injection-Annotation konfiguriert.
  • Der traefik-Namespace wird ebenfalls mit linkerd.io/inject: enabled annotiert,
    • damit Ingress-Traffic zum blog-content Service per mTLS gesichert ist.

Ressourcen-Limits:

  • Proxy: 64Mi Request, 128Mi Limit (angepasst an 3-Node-Cluster).
  • Control Plane: Standardwerte mit angepassten Requests fuer kleinen Cluster.

Parent links: SWR029 Service Mesh mit automatischem mTLS (Linkerd)

23 Default-Deny AuthorizationPolicies fuer Linkerd Service Mesh SWA023

Linkerd AuthorizationPolicies werden im Default-Deny-Modus konfiguriert. Pro Service wird ein Server-Objekt (policy.linkerd.io/v1beta3) fuer den Applikations-Port erstellt. Ohne eine passende AuthorizationPolicy ist kein eingehender Traffic erlaubt (Default-Deny).

Erlaubte Kommunikationspfade fuer blog-content:

  • Traefik Ingress Controller (identifiziert ueber MeshTLSAuthentication mit
    • der ServiceAccount-Identitaet traefik.traefik) darf HTTP-Traffic an den blog-content Service senden.
  • Kubelet Health-Probes (identifiziert ueber NetworkAuthentication) duerfen
    • die Liveness- und Readiness-Endpunkte erreichen.

Alle anderen eingehenden Verbindungen werden vom Linkerd-Proxy abgelehnt. Neue Services muessen explizit durch eine AuthorizationPolicy freigeschaltet werden, bevor sie blog-content erreichen koennen.

Parent links: SWR029 Service Mesh mit automatischem mTLS (Linkerd)

24 Outbound Port und Adapter für Markdown-Rendering SWA024

Das Markdown-Rendering wird über einen dedizierten Outbound Port (MarkdownRenderer) abstrahiert. 28 Featured-Post-Abfrage im Persistence Adapter SWA028

Der JPA Persistence Adapter wird um eine Abfrage für aktuell gefeatured Posts erweitert:

  • Das PostRepository-Interface (Outbound Port) erhält die Methode
    • findFeaturedByTenantId(TenantId, LocalDate): List.
  • Die JPA-Implementierung verwendet eine JPQL-Query mit Filterung auf
    • Status PUBLISHED, featuredFrom <= aktuelles Datum und featuredUntil >= aktuelles Datum.
  • Sortierung nach featuredFrom absteigend.
  • Der Thymeleaf-Controller (LandingPageController oder PostViewController)
    • ruft die neue Repository-Methode auf und übergibt das Ergebnis als Modell-Attribut an das Template.

29 User-Management-Service Architektur (hexagonal) SWA029

Der User-Management-Service folgt der hexagonalen Architektur (SWA-001):

  • Domain Layer: UserProfile (Aggregate Root) mit OidcSubject, E-Mail,
    • DisplayName, ApprovalStatus (PENDING, APPROVED, REJECTED), Rollen (Set) und TenantMemberships (Set). Role ist ein Enum (SUPERADMIN, ADMIN, AUTHOR, REVIEWER, READER). Der SUPERADMIN-Account wird beim Service-Start aus Infrastruktur- Konfiguration (Umgebungsvariable/Secret) angelegt oder aktualisiert. TenantMembership ist ein Value Object (TenantId, Role). TenantSettings Value Object mit LoginMode (INTERNAL, OIDC, BOTH), autoApproveOidc (boolean) und autoApproveEmailDomains (Set).
  • Application Layer: UserProfileUseCase (Inbound Port) mit Operationen
    • syncFromOidc, syncFromInternal, findByOidcSubject, findByUsername, assignRole, removeRole, approveUser, addTenantMembership, removeTenantMembership. TenantSettingsUseCase fuer Login-Modus- Konfiguration. UserProfileRepository (Outbound Port) fuer Persistenz.
  • Adapter Layer Inbound: REST-Controller (UserController) unter /api/users.
  • Adapter Layer Outbound: JPA-basierte PostgreSQL-Persistenz mit Flyway-
    • Migrationen. Eigene Datenbank (Database per Service).
  • Optional: OIDC-Gruppen-Attribute werden aus dem ID Token extrahiert
    • und auf plattforminterne Rollen gemappt (konfigurierbar).
  • Der Service hat keine eigene Web-UI. Administration erfolgt ueber
    • die Blog-Content-Service-Admin-Oberflaeche (spaeter).

Parent links: SWR007 Rollenbasierte Zugriffskontrolle, SWR043 User-Management-Service fuer Profile, Rollen und Tenant-Zuordnung

30 Deklarative Datenbank-Ressourcen pro Service SWA030

Jeder Service, der eine PostgreSQL-Datenbank benoetigt, erhaelt eine dedizierte CloudNativePG Database-Ressource (CRD). Die Database-Ressource definiert den Datenbanknamen, den Owner und die Zuordnung zum Cluster. Aktuelle Datenbanken:

  • blog_content (blog-content Service)
  • user_management (user-management Service)
  • tenant_management (tenant-management Service)
    • Die Cluster-Definition nutzt einen neutralen Platzhalter (database: app) im initdb-Block. Weitere Service-Datenbanken werden durch Hinzufuegen weiterer Database-Manifeste erstellt. Die Migration bestehender Datenbanken erfolgt durch Erstellen der Database-Ressource (adopt existing).

Parent links: SWR010 Container-Image und Health-Checks

31 Audit-Logging-Architektur SWA031

Audit-Logging wird als Cross-Cutting Concern über den Shared Kernel bereitgestellt und in jedem Service lokal persistiert.

Shared Kernel stellt bereit:

  • AuditLogEntry: Framework-freies Record mit id, timestamp, tenantId,
    • actor, action, entityType, entityId, details
  • AuditLogger: Interface (Outbound Port) mit log(AuditLogEntry)

Jeder Service implementiert:

  • JpaAuditLogEntity: JPA-Entity für die audit_log Tabelle
  • JpaAuditLogger: Adapter der AuditLogger implementiert
  • Flyway-Migration für die audit_log Tabelle

Die audit_log Tabelle ist append-only. Es gibt keine UPDATE- oder DELETE-Operationen auf dieser Tabelle. Die Application Services rufen AuditLogger.log() nach erfolgreichen schreibenden Operationen auf.

Der actor wird über den SecurityContext ermittelt (SecurityAuditorAware-Pattern analog zur JPA-Auditing-Konfiguration).

Parent links: SWR056 Audit-Logging für alle relevanten Aktionen

32 Redis als externer Session-Store SWA032

HTTP-Sessions werden über Spring Session Data Redis in einer externen Redis-Instanz gespeichert (ADR-0030). Redis läuft als Single-Instance Deployment im eigenen Kubernetes-Namespace (redis). Die Verbindung zwischen Blog-Pod und Redis ist durch Linkerd mTLS gesichert. Redis wird ohne Persistenz (kein RDB/AOF) betrieben, da Sessions kurzlebig und reproduzierbar sind. Passwort-Authentifizierung ist über ein Kubernetes-Secret konfiguriert. Network Policies beschränken den Zugriff auf Redis auf den tomsblog Namespace.

Parent links: SWR057 Externer Session-Store für Blog Content Service

33 Shared UI Library Architektur SWA033

Die gemeinsame UI-Bibliothek wird als Maven-Modul libs/shared-ui bereitgestellt (analog zu libs/shared-kernel, SWA-002). Die Library enthält ausschließlich Thymeleaf-Template-Fragmente und statische CSS-Ressourcen, keine Java-Klassen.

Struktur:

  • src/main/resources/templates/shared/layout/default.html
    • Master-Layout mit Pico CSS, Header-/Footer-Einbindung
  • src/main/resources/templates/shared/fragments/footer.html
    • Einheitlicher Footer (Copyright, Impressum, Datenschutz, Version)
  • src/main/resources/static/css/custom.css
    • Plattformweite CSS-Anpassungen (Sticky Footer, Branding-Hooks)

Services binden shared-ui als Maven-Dependency ein. Thymeleaf löst Templates über den Classpath auf, sodass shared/ Prefix Templates aus dem JAR der Library geladen werden. Header-Fragmente verbleiben in den jeweiligen Services, da sie service-spezifische Navigation enthalten.

Die Library hat Spring Boot Starter Thymeleaf und Thymeleaf Layout Dialect als provided Dependencies. Sie enthält keine Spring-Konfiguration oder Auto-Configuration.

36 Auditlog-View Architektur SWA036

Die Auditlog-View folgt der hexagonalen Architektur jedes Services:

Inbound Port:

  • AuditLogQueryUseCase: Interface im Application Layer mit Methoden
    • zur paginierten und gefilterten Abfrage von Audit-Einträgen
  • AuditLogSearchCriteria: Record mit optionalen Filterfeldern
    • (action, entityType, actor, from, to, searchTerm)

Application Service:

  • AuditLogQueryService: Implementiert AuditLogQueryUseCase,
    • delegiert an den Outbound Port

Outbound Port:

  • AuditLogRepository (Erweiterung): Methoden für paginierte und
    • gefilterte Abfragen

Inbound Adapter:

  • AuditLogAdminController: Thymeleaf-Controller unter /admin/audit-logs
  • AuditLogViewDto: DTO für die Template-Darstellung

Outbound Adapter:

  • SpringDataAuditLogRepository: Erweiterung um JPA Specification-
    • basierte Abfragen für dynamische Filterung

Da jeder Service seine eigene audit_log-Tabelle besitzt (Database per Service), zeigt jeder Service nur seine eigenen Audit-Einträge an. Der Blog Content Service wird als erster Service mit der Auditlog-View ausgestattet. Die Architektur ist so gestaltet, dass User Management und Tenant Management Service dieselbe Struktur übernehmen können.

37 RabbitMQ-Adapter mit Quorum Queues und Dead-Letter-Handling SWA037

Der RabbitMQ Outbound Adapter konfiguriert eine Topic Exchange (tomsblog.tasks) mit folgenden Quorum Queues:

  • translation.requests (Routing Key: task.translation)
  • tts.generation (Routing Key: task.tts)
  • snapshot.requests (Routing Key: task.snapshot)

Jede Queue besitzt eine Dead-Letter-Exchange (tomsblog.tasks.dlx) mit zugehöriger Dead-Letter-Queue (*.dlq) für fehlgeschlagene Nachrichten. Die Konfiguration erfolgt deklarativ über Spring AMQP Beans (Queue, Exchange, Binding).

Das Package adapter.outbound.rabbitmq enthält:

  • RabbitMqTaskPublisher: Implementiert TaskPublisher Port
  • RabbitMqConfiguration: Deklariert Exchanges, Queues, Bindings
  • TaskRoutingKeyResolver: Bestimmt den Routing Key pro Nachrichtentyp
