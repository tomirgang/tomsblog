Ein Post kann über POST /api/posts/{id}/publish veröffentlicht werden. Dabei wird der Status auf PUBLISHED gesetzt und ein PostPublishedEvent erzeugt. Ein bereits veröffentlichter Post kann nicht erneut veröffentlicht werden.

7.0 Rollenbasierte Zugriffskontrolle SWR007

Das System muss fünf Rollen unterstützen: SUPERADMIN, ADMIN, AUTHOR, REVIEWER, READER. SUPERADMIN verwaltet Tenants und die Plattform-Konfiguration. Sein Passwort wird ausschließlich über die Infrastruktur gesetzt (Umgebungsvariable/Secret). Es gibt genau einen SUPERADMIN pro Plattform-Instanz. ADMIN verwaltet Benutzer und Inhalte innerhalb eines Tenants und gibt neue Benutzer frei (STK028). AUTHOR darf Posts erstellen, bearbeiten und veröffentlichen. REVIEWER darf Posts lesen und Review-Feedback geben, aber nicht erstellen. READER hat nur Lesezugriff auf veröffentlichte Posts. Nicht angemeldete Benutzer werden wie READER behandelt (STK029).

16 OIDC Login mit Authentik als externem Provider SWR016

Das System muss OpenID Connect (OIDC) Login über Authentik (https://auth.do9ita.de) als externen Identity Provider unterstützen (siehe ADR-0027). Der Authorization Code Flow mit PKCE wird verwendet. Services, die eine Web-Oberfläche bereitstellen (z.B. Blog Content Service), agieren als OAuth2 Client (Spring Security OAuth2 Login). API-Endpunkte werden als OAuth2 Resource Server geschützt und validieren Authentik-JWTs. Authentik übernimmt Login-Flows, MFA, Session-Management und Passwort-Policies. Dies ersetzt die einfache formbasierte Admin-Authentifizierung (SWR-028). Optional können Gruppen-Attribute aus dem OIDC ID Token (groups Claim) übernommen und auf plattforminterne Rollen gemappt werden. Das Mapping ist pro Tenant konfigurierbar.

18 Automatisierte Kommentar-Moderation via LLM SWR018

Neue Kommentare müssen automatisiert durch ein LLM überprüft werden. Die Überprüfung nutzt das OpenRouter-Backend und bewertet Kommentare auf Spam, Beleidigungen und Off-Topic-Inhalte. Kommentare werden automatisch als approved, rejected oder review_pending klassifiziert. Bei LLM-Ausfall greift Graceful Degradation (Kommentar wird als review_pending markiert).

Das Kommentarsystem muss Shadow-Banning unterstützen. Ein shadow-gebannter Benutzer sieht seine eigenen Kommentare weiterhin normal, andere Benutzer sehen diese Kommentare jedoch nicht. Administratoren und Autoren können Shadow-Bans vergeben und aufheben.

20 Tag CRUD API SWR020

21 Translation CRUD API SWR021

Das System muss eine REST API für die Verwaltung von Übersetzungen bereitstellen: POST /api/posts/{postId}/translations (Übersetzung erstellen), GET /api/posts/{postId}/translations (alle Übersetzungen eines Posts), GET /api/posts/{postId}/translations/{id} (einzelne Übersetzung lesen), PUT /api/posts/{postId}/translations/{id} (Übersetzung aktualisieren), POST /api/posts/{postId}/translations/{id}/approve (Übersetzung freigeben), POST /api/posts/{postId}/translations/{id}/reject (Übersetzung ablehnen), DELETE /api/posts/{postId}/translations/{id} (Übersetzung löschen). Alle Endpunkte sind Tenant-scoped über den X-Tenant-Id Header.

22 Time-based Auto Publishing SWR022

Das System muss zeitgesteuerte Veröffentlichung (Scheduled Publishing) unterstützen:

  • Ein Post kann mit einem zukünftigen Veröffentlichungszeitpunkt (publishAt) versehen werden.
  • Ein Scheduler prüft periodisch, ob Posts zur Veröffentlichung anstehen.
  • Zum geplanten Zeitpunkt wird der Post automatisch in den Status PUBLISHED überführt.
  • Ein PostPublishedEvent wird dabei ausgelöst (wie bei manueller Veröffentlichung).
  • Der Autor kann den geplanten Zeitpunkt bis zur Veröffentlichung ändern oder stornieren.
  • Die REST API wird um das Feld publishAt erweitert (optional bei POST/PUT /api/posts/{id}).

Parent links: STK013 Zeitgesteuerte Veröffentlichung

23 Fuzz Testing externer Interfaces SWR023

Alle externen Interfaces (REST-Endpoints) müssen durch Fuzz Tests abgesichert werden:

  • Jeder öffentliche REST-Endpoint muss einen zugehörigen Fuzz Test besitzen.
  • Fuzz Tests senden zufällige/ungültige Eingaben an die Endpoints.
  • Kein Fuzz-Input darf einen HTTP 5xx Statuscode auslösen (Server Error).
  • Fuzz Tests verwenden Jazzer mit JUnit 5 Integration (@FuzzTest).
  • Fuzz Tests werden als Teil des regulären Test-Lifecycles ausgeführt (Regression Mode).
  • Gefundene Crash-Inputs werden als Corpus-Dateien versioniert.

Parent links: STK012 Sicherheit (OWASP Top 10)

24 OpenAPI/Swagger API-Dokumentation SWR024

Jeder REST-Service muss eine maschinenlesbare OpenAPI 3.x Spezifikation bereitstellen:

  • Die Spezifikation wird automatisch aus dem Code generiert (springdoc-openapi).
  • Alle Endpunkte, Request/Response-Schemas und Parameter müssen dokumentiert sein.
  • Ein Swagger UI muss unter /swagger-ui.html erreichbar sein.
  • Die OpenAPI JSON-Spezifikation muss unter /api-docs abrufbar sein.
  • Der X-Tenant-Id Header muss als erforderlicher Parameter dokumentiert werden.
  • Jede Operation muss einen Summary-Text und die möglichen HTTP-Statuscodes enthalten.

25 Thymeleaf Layout-Grundgerüst (responsiv) SWR025

Der Blog Content Service stellt ein responsives Thymeleaf-Layout als Server-Side-Rendering-UI bereit:

  • Ein zentrales Layout-Template mit Header, Navigation, Content-Bereich und Footer.
  • Thymeleaf Layout Dialect für deklarative Template-Vererbung (layout:decorate).
  • PicoCSS als classless CSS-Framework für responsives Design ohne Build-Tooling.
  • Semantische HTML5-Struktur (header, nav, main, footer).
  • Dark/Light Mode Support via prefers-color-scheme (durch PicoCSS).
  • Wiederverwendbare Fragments für Header und Footer.
  • Eigene CSS-Datei für minimale Anpassungen und Tenant-Branding-Hooks.
  • Der Web-Controller bildet einen eigenen Inbound Adapter (adapter/inbound/web/).

26 Öffentliche Blog-Ansicht (Post-Liste und Einzelansicht) SWR026

Der Blog Content Service muss eine öffentliche Thymeleaf-basierte Blog-Ansicht bereitstellen:

  • Die Landing Page (/) und /posts zeigen beide dieselbe Post-Liste mit allen veröffentlichten Posts des Tenants in absteigender chronologischer Reihenfolge (neueste zuerst).
  • Die Post-Liste zeigt pro Eintrag: Titel, Veröffentlichungsdatum, Klartext-Kurzvorschau (max. 200 Zeichen, HTML-Tags entfernt) und einen Link zur Einzelansicht.
  • Die Einzelansicht unter /posts/{slug} zeigt einen veröffentlichten Post mit: Titel, Veröffentlichungsdatum, Volltext, Quellen und Tags.
  • Nicht veröffentlichte Posts (DRAFT, ARCHIVED) sind in der öffentlichen Ansicht nicht sichtbar.
  • Die Slug-basierte URL ist SEO-freundlich und leserlich.
  • Das PostRepository muss eine Methode zur Abfrage veröffentlichter Posts und zur Suche nach Slug bereitstellen.
  • Die Views nutzen das bestehende Layout-Grundgerüst (SWR-025) via Thymeleaf Layout Dialect.
  • Beide Views sind ohne Authentifizierung zugänglich (öffentliche Ansicht).

Parent links: STK001 Blog-Posts erstellen und veröffentlichen

27 Thymeleaf-Formular zum Erstellen und Bearbeiten von Posts SWR027

Der Blog Content Service muss ein Thymeleaf-basiertes Formular bereitstellen, mit dem Posts erstellt und bearbeitet werden können:

  • Ein Formular unter /posts/new ermöglicht das Erstellen eines neuen Posts mit Feldern für Titel, Inhalt, Sprache (Locale), Social-Media-Titel (optional) und Social-Media-Zusammenfassung (optional).
  • Ein Formular unter /posts/{id}/edit ermöglicht das Bearbeiten eines bestehenden Posts (gleiche Felder wie beim Erstellen, vorausgefüllt mit den aktuellen Werten).
  • Nach erfolgreichem Erstellen oder Bearbeiten wird der Benutzer zur Post-Liste weitergeleitet (/posts).
  • Das Formular validiert serverseitig: Titel und Inhalt dürfen nicht leer sein.
  • Bei Validierungsfehlern wird das Formular erneut angezeigt mit Fehlermeldungen und den eingegebenen Werten.
  • Die Post-Liste (/posts) enthält einen Link zum Erstellen eines neuen Posts.
  • Jeder Post in der Liste enthält einen Link zum Bearbeiten.
  • Die Views nutzen das bestehende Layout-Grundgerüst (SWR-025) via Thymeleaf Layout Dialect.
  • Der Controller nutzt die bestehenden Inbound Ports (PostUseCase) mit CreatePostCommand und UpdatePostCommand.
  • Die TenantId und AuthorId werden aus dem Request-Header (X-Tenant-Id, X-Author-Id) bezogen.

Parent links: STK001 Blog-Posts erstellen und veröffentlichen

28 Einfacher Admin-Login zum Schutz der Schreiboperationen SWR028

Der Blog Content Service schuetzt alle Schreiboperationen ueber Spring Security:

  • Spring Security sichert alle schreibenden Endpunkte (POST, PUT,
    • DELETE auf /api/ sowie POST /posts, GET /posts/new, GET /posts/{id}/edit).
  • Die oeffentliche Web-Ansicht (GET /posts, GET /posts/{slug}) zeigt
    • nur veroeffentlichte Posts (Status PUBLISHED) an.
  • Nach Login zeigt die Web-Ansicht (GET /posts) alle Posts inklusive
    • Drafts und archivierte Posts mit Status-Anzeige.
  • Die REST-API (GET /api/posts/) ist vollstaendig geschuetzt und
    • zeigt alle Posts unabhaengig vom Status.
  • Die Authentifizierung erfolgt ueber den User-Management-Service
    • (ADR-0032). Unauthentifizierte Benutzer werden per Redirect auf /auth/login weitergeleitet.
  • Das Break-Glass Admin-Login (SUPERADMIN) ist unter /auth/admin/login
    • im User-Management-Service verfuegbar.
  • Nach erfolgreichem Login wird der Benutzer auf die Post-Liste
    • weitergeleitet.
  • Ein Logout-Link ist im Header sichtbar, wenn der Benutzer
    • eingeloggt ist.
  • Die REST-API (/api/**) nutzt HTTP Basic Authentication als
    • Alternative zum formbasierten Login.
  • Die Session wird ueber Redis geteilt (SWR-064), sodass der Blog
    • Content Service die vom User-Management-Service erstellte Session direkt nutzen kann.

Parent links: STK005 Benutzerverwaltung und Rollen, SWR007 Rollenbasierte Zugriffskontrolle

29 Service Mesh mit automatischem mTLS (Linkerd) SWR029

Das System muss ein Service Mesh (Linkerd) verwenden, das folgende Anforderungen erfüllt:

  • Alle Service-zu-Service-Verbindungen im Kubernetes-Cluster werden automatisch mit mTLS verschlüsselt.
  • Jeder Service erhält eine kryptografische Identität basierend auf seinem Kubernetes ServiceAccount.
  • AuthorizationPolicies definieren erlaubte Kommunikationspfade (Default-Deny).
  • Nur explizit konfigurierte Service-zu-Service-Verbindungen sind zulässig.
  • Certificates werden automatisch rotiert (kein manuelles Key-Management).
  • Die Installation erfolgt über Helm Charts und wird via Flux (GitOps) verwaltet.

Parent links: STK014 Sichere Service-zu-Service-Kommunikation (Zero Trust)

Child links: SWA022 Linkerd Service Mesh Deployment via Flux und cert-manager, SWA023 Default-Deny AuthorizationPolicies fuer Linkerd Service Mesh

30 User-Kontext-Propagierung für geschützte Features SWR030

Das System muss einen User-Kontext durch die Service-Kette propagieren:

  • Das API-Gateway validiert JWT-Token und extrahiert User-Claims (User-ID, Rollen, Tenant).
  • Aufrufende Services propagieren den User-Kontext als HTTP-Header (X-User-Id, X-User-Roles, X-Tenant-Id).
  • Aufgerufene Services prüfen sowohl die Linkerd-Service-Identität als auch die User-Claims.
  • KI-Features (Übersetzung, Schreibassistenz, Bildgenerierung) lehnen Anfragen ohne gültigen User-Kontext mit HTTP 403 ab.
  • Nur Benutzer mit der Rolle AUTHOR oder ADMIN dürfen KI-Features auslösen.
  • Der propagierte User-Kontext wird für Audit-Logging und Rate-Limiting verwendet.

Parent links: STK015 KI-Features nur für autorisierte Benutzer, SWR029 Service Mesh mit automatischem mTLS (Linkerd)

31 Secrets verschlüsselt im Repository und automatisch synchronisiert SWR031

Sensible Zugangsdaten (Passwörter, API-Keys, Tokens) dürfen nicht im Klartext im Git-Repository gespeichert werden. Sie müssen vor dem Commit verschlüsselt werden und beim Deployment automatisch entschlüsselt werden. Operator-generierte Secrets (z.B. Datenbank-Credentials) müssen automatisch in die Namespaces der konsumierenden Services synchronisiert werden, ohne manuelle Kopiervorgänge.

Das Domain-Modell TenantSettings wird um die Felder oidcRoleMappingEnabled (boolean, default false) und oidcRoleMappings (Map) erweitert.

oidcRoleMappings definiert ein Mapping von OIDC-Gruppennamen auf plattforminterne Rollen (z.B. {"blog-authors": "AUTHOR", "blog-admins": "ADMIN"}).

Wenn oidcRoleMappingEnabled aktiviert ist, wird bei jedem OIDC-Login der groups-Claim des ID-Tokens ausgewertet:

  • Für jede Gruppe im Claim wird das konfigurierte Mapping geprüft.
  • Die höchste gemappte Rolle wird dem Benutzer zugewiesen.
  • Wenn keine Gruppe matcht, wird die Standard-Rolle (SWR-094)
    • zugewiesen.
  • Manuell vergebene Rollen werden durch die OIDC-Rolle
    • überschrieben.

Die Admin-UI zeigt im OIDC-Bereich der Tenant-Einstellungen:

  • Einen Toggle für oidcRoleMappingEnabled.
  • Eine dynamische Liste von Mapping-Einträgen (OIDC-Gruppenname
    • → Rolle) mit Hinzufügen/Entfernen-Funktionalität.

Das SUPERADMIN-Mapping ist nicht erlaubt (wird bei Eingabe abgelehnt).
