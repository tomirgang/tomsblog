Backup & Recovery

1. Übersicht

PostgreSQL-Backups werden über CloudNativePG Barman Object Store auf einen externen S3-kompatiblen Speicher (Garage auf Netcup VM) gesichert. Sowohl tägliche Base Backups als auch kontinuierliches WAL-Streaming sind konfiguriert.

2. Recovery-Ziele

Parameter Zielwert

RPO (Recovery Point Objective)

< 1 Stunde (WAL-Streaming)

RTO (Recovery Time Objective)

< 15 Minuten (Restore aus Backup)

3. Backup-Architektur

4. Konfiguration

4.1. S3-Credentials

Die Zugangsdaten für den Garage-Bucket liegen als Kubernetes Secret im Namespace postgres:

apiVersion: v1
kind: Secret
metadata:
  name: backup-s3-credentials
  namespace: postgres
type: Opaque
stringData:
  ACCESS_KEY_ID: "<Access Key aus Garage>"
  SECRET_ACCESS_KEY: "<Secret Key aus Garage>"

4.2. CloudNativePG Cluster (Backup-Sektion)

spec:
  backup:
    barmanObjectStore:
      destinationPath: s3://postgres-backup/
      endpointURL: https://garage.do9ita.de
      s3Credentials:
        accessKeyId:
          name: backup-s3-credentials
          key: ACCESS_KEY_ID
        secretAccessKey:
          name: backup-s3-credentials
          key: SECRET_ACCESS_KEY
      wal:
        compression: gzip
        maxParallel: 2
    retentionPolicy: "30d"

4.3. ScheduledBackup

Tägliche Base Backups werden um 02:00 UTC erstellt:

apiVersion: postgresql.cnpg.io/v1
kind: ScheduledBackup
metadata:
  name: postgres-daily-backup
  namespace: postgres
spec:
  schedule: "0 2 * * *"
  backupOwnerReference: self
  cluster:
    name: postgres-cluster
  method: barmanObjectStore
  immediate: true

Das Flag immediate: true löst beim Erstellen der Ressource sofort ein initiales Backup aus.

5. Garage-Bucket einrichten

Auf der Netcup VM muss ein dedizierter Bucket mit API-Key existieren:

docker compose exec garage /garage bucket create postgres-backup
docker compose exec garage /garage key create postgres-backup-key
docker compose exec garage /garage bucket allow --read --write --owner postgres-backup --key postgres-backup-key

Die Ausgabe von garage key info postgres-backup-key enthält Access Key und Secret Key für das Kubernetes Secret.

5.1. Voraussetzungen an Garage

  • Version: mindestens v1.3.0 (STREAMING-AWS4-HMAC-SHA256-PAYLOAD Support, benötigt von barman-cloud)

  • S3-Region: muss in garage.toml auf us-east-1 gesetzt sein, da barman-cloud diese Region als Default verwendet und CloudNativePG kein Region-Feld unterstützt:

    [s3_api]
s3_region = "us-east-1"

5.2. Deployment via Kustomize

Damit Flux die Backup-Ressourcen deployed, müssen sie in der Kustomization referenziert sein:

# infra/k8s/kustomization.yaml
resources:
  - postgres/namespace.yaml
  - postgres/backup-s3-credentials.yaml
  - postgres/cluster.yaml
  - postgres/scheduled-backup.yaml

6. Disaster Recovery

6.1. Restore aus dem letzten Backup

Ein neuer Cluster kann durch einen Recovery-Bootstrap aus dem Object Store erstellt werden:

apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: postgres-cluster-restored
  namespace: postgres
spec:
  instances: 2
  bootstrap:
    recovery:
      source: postgres-cluster-backup
  externalClusters:
    - name: postgres-cluster-backup
      barmanObjectStore:
        destinationPath: s3://postgres-backup/
        endpointURL: https://garage.do9ita.de
        s3Credentials:
          accessKeyId:
            name: backup-s3-credentials
            key: ACCESS_KEY_ID
          secretAccessKey:
            name: backup-s3-credentials
            key: SECRET_ACCESS_KEY
  storage:
    size: 10Gi
    storageClass: hcloud-volumes

6.2. Point-in-Time Recovery (PITR)

Für eine Wiederherstellung auf einen bestimmten Zeitpunkt wird recoveryTarget ergänzt:

  bootstrap:
    recovery:
      source: postgres-cluster-backup
      recoveryTarget:
        targetTime: "2026-05-03T12:00:00Z"

6.3. Ablauf eines Disaster Recovery

  1. Ausfall feststellen und Ursache analysieren

  2. Entscheiden: Restore letztes Backup oder PITR auf bestimmten Zeitpunkt

  3. Recovery-Cluster-Manifest erstellen (siehe oben)

  4. kubectl apply -f postgres-cluster-restored.yaml

  5. Warten bis der Cluster Ready ist: kubectl -n postgres get cluster

  6. Services auf den neuen Cluster umkonfigurieren (JDBC-URL anpassen)

  7. Datenintegrität prüfen

  8. Alten Cluster entfernen

7. Monitoring

7.1. Backup-Status prüfen

# Letzte Backups anzeigen
kubectl -n postgres get backups

# Cluster-Status inkl. letztem erfolgreichem Backup
kubectl -n postgres get cluster postgres-cluster -o yaml | grep -A5 lastSuccessfulBackup

7.2. Alerting (empfohlen)

Wenn Prometheus/Grafana eingerichtet ist (Phase 9), sollte ein Alert konfiguriert werden, der auslöst, wenn das letzte erfolgreiche Backup älter als 26 Stunden ist.

8. Offene Punkte

  • Automatisierte Restore-Tests (z.B. wöchentlicher Test-Restore in separaten Namespace)

  • Alerting bei fehlgeschlagenen Backups (nach Phase 9: Observability)

9. Troubleshooting

9.1. AuthorizationHeaderMalformed / Bad Request auf HeadBucket

Garage erwartet die korrekte Region in der S3v4-Signatur. Prüfen:

grep s3_region /path/to/garage.toml
# Muss "us-east-1" sein

9.2. Invalid content sha256 hash (STREAMING-AWS4-HMAC-SHA256-PAYLOAD)

Garage v1.0.x unterstützt kein Chunked Transfer Encoding mit SHA256. Upgrade auf mindestens v1.3.0.

9.3. Secret "backup-s3-credentials" not found

Das Secret muss in der Kustomization referenziert sein und vor dem Cluster-Manifest deployed werden.
