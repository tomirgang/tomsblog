Rollback-Verfahren

1. Deployment-Rollback

1.1. Via Git Revert (empfohlen, GitOps-konform)

Der sicherste Weg ist ein Git Revert des problematischen Commits. Flux erkennt den neuen Commit und reconciled:

git revert <problematischer-commit>
git push
# Flux reconciled automatisch innerhalb von 10 Minuten

Manuelles Triggern für sofortige Wirkung:

flux reconcile source git tomsblog
flux reconcile kustomization tomsblog

1.2. Via kubectl (Notfall)

In dringenden Fällen kann direkt im Cluster zurückgerollt werden:

# Letzte Revision anzeigen
kubectl rollout history deployment/blog-content -n tomsblog

# Auf vorherige Revision zurückrollen
kubectl rollout undo deployment/blog-content -n tomsblog

# Auf spezifische Revision
kubectl rollout undo deployment/blog-content -n tomsblog --to-revision=3
Direkte kubectl-Änderungen werden beim nächsten Flux-Reconcile überschrieben. Daher muss parallel ein Git Revert erfolgen.

2. Pod-Neustart (ohne Rollback)

Falls nur ein Neustart nötig ist (z.B. nach Config-Änderung):

kubectl rollout restart deployment/blog-content -n tomsblog

3. PostgreSQL-Failover

Bei Datenbankproblemen kann ein manuelles Switchover ausgelöst werden:

# Status prüfen
kubectl get cluster postgres-cluster -n postgres

# Manuelles Switchover (Replica wird Primary)
kubectl cnpg promote postgres-cluster -n postgres
