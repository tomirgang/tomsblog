1.0 Hexagonale Architektur pro Service SWA001

Jeder Microservice folgt der hexagonalen Architektur mit den Schichten: domain/ (reine Fachlogik, keine Framework-Abhängigkeiten), application/ (Ports, Use Cases), adapter/inbound (REST Controller, Event Listener), adapter/outbound (JPA Repositories, Kafka Producer, HTTP Clients).

2.0 Shared Kernel als Framework-freie Library SWA002

Gemeinsame Domain Primitives (EntityId, TenantId, AuthorId, AggregateRoot, DomainEvent, Auditable) werden in libs/shared-kernel bereitgestellt. Diese Library darf keine Spring- oder Framework-Abhängigkeiten haben.

3.0 Event-Contracts als geteilte Library SWA003

Alle Cross-Service Events (PostCreatedEvent, PostUpdatedEvent, PostPublishedEvent) und die gemeinsame EventMetadata werden in libs/event-contracts definiert. Consumer und Producer verwenden dieselben Event-Klassen.

5.0 Kafka als Event-Broker SWA005

Apache Kafka (KRaft Mode) dient als zentraler Event-Broker. Topics werden pro Event-Typ angelegt. Consumer Groups ermöglichen unabhängige Verarbeitung.

6.0 AI Service als separater Adapter SWA006

Die KI-Integration (OpenRouter) wird als Outbound-Adapter im Blog Content Service implementiert. Bei Ausfall liefert der Adapter einen definierten Fehler; die restliche Funktionalität bleibt unberührt (Circuit Breaker Pattern).

Parent links: SWR004 Übersetzung per KI (Author-getriggert), SWR014 Graceful Degradation bei KI-Ausfall

7.0 Domain-Modell mit Aggregates, Entities und Value Objects SWA007

Das Domain-Modell des Blog Content Service besteht aus folgenden Bausteinen:

  • Post (Aggregate Root): PostId, TenantId, AuthorId (Referenz), title, slug, content, status, locale, tags (Set), sources (List), attachments (List)
  • Tag (Entity): TagId, TenantId, name, slug
  • Translation (Aggregate Root): TranslationId, PostId, TenantId, locale, title, content, status, source
  • Source (Value Object): url, title
  • Attachment (Value Object): AttachmentId, filename, contentType, size, show, storageKey
  • AuthorId liegt im shared-kernel als reine Referenz (keine Author-Entity im blog-content)
    • Alle Aggregates und Entities tragen eine TenantId fuer Multi-Tenant-Isolation. Attachments mit show=true werden im Blog-Rendering angezeigt, mit show=false fuer eingebettete Inhalte.

8.0 Translation als separates Aggregate mit eigenem Lifecycle SWA008

Uebersetzungen werden als eigenes Aggregate modelliert (nicht als Child im Post). Der Lifecycle ist: DRAFT -> REVIEW_PENDING -> APPROVED oder REJECTED. AI-generierte Uebersetzungen starten in REVIEW_PENDING (Autor muss pruefen). Manuelle Uebersetzungen starten in DRAFT. Bei Aenderung einer approbierten Uebersetzung wechselt der Status auf REVIEW_PENDING.

Parent links: SWR004 Übersetzung per KI (Author-getriggert), SWR005 Manuelle Übersetzung

Child links: IMP009 Translation Aggregate, IMP016 TranslationService und TranslationUseCase

9.0 gRPC für synchrone Service-Kommunikation SWA009

Für synchrone Kommunikation zwischen Microservices wird gRPC verwendet. Kafka bleibt für asynchrone, event-basierte Kommunikation zuständig. gRPC bietet typsichere Contracts via Protobuf, effizientes Binary-Protokoll und native Streaming-Unterstützung. Service-Interfaces werden als .proto-Dateien in einer geteilten Library definiert.

Parent links: SWR009 Domain Events via Kafka

10 Custom Auth Service als eigener Microservice SWA010

Die Authentifizierung und Autorisierung wird als eigener Microservice implementiert (kein Keycloak). Der Auth Service unterstützt OIDC als Relying Party und stellt JWTs für die interne Service-Kommunikation aus. Andere Services validieren Tokens lokal via Public Key.

Parent links: SWR007 Rollenbasierte Zugriffskontrolle, SWR016 Custom Identity Provider mit OIDC

11 Domain-basierte Tenant-Resolution am Ingress SWA011

Die Tenant-Auflösung erfolgt am Ingress-Level über den Host-Header. Ein Tenant-Resolution-Service mappt Domains auf TenantIds. Ein Tenant kann mehrere Domains besitzen (Custom-Domain + Plattform-Subdomain). Die aufgelöste TenantId wird als Header (X-Tenant-Id) an nachgelagerte Services propagiert.

Parent links: SWR003 Tenant-Isolation auf Datenebene, SWR017 Domain-basierte Tenant-Auswahl

12 LLM-basierte Kommentar-Moderation als Adapter SWA012

Die automatisierte Kommentar-Überprüfung wird als Outbound-Adapter im Kommentar-Service implementiert. Der Adapter nutzt das OpenRouter-Backend (analog zum AI-Adapter im Blog Content Service, SWA-006). Das Moderation-Interface ist als Port definiert, sodass der LLM-Adapter austauschbar bleibt (z.B. durch regelbasierte Moderation als Fallback).

Parent links: SWR018 Automatisierte Kommentar-Moderation via LLM

13 Flyway für versionierte Datenbank-Migrationen SWA013

Alle Datenbank-Schema-Änderungen werden über Flyway-Migrationen verwaltet. Migrationsdateien liegen unter src/main/resources/db/migration/ mit dem Benennungsschema V{nummer}__{beschreibung}.sql. Hibernate ddl-auto ist auf validate gesetzt (nur Validierung, keine Änderung). Flyway wird beim Service-Start automatisch ausgeführt.

Parent links: SWR001 Post CRUD API, SWR020 Tag CRUD API, SWR021 Translation CRUD API

Child links: IMP015 JpaTagRepository (Outbound Adapter), IMP018 JpaTranslationRepository (Outbound Adapter), IMP019 Flyway Migrationen für Blog Content Service
