1.0 Post CRUD API SWR001

Das System muss eine REST API bereitstellen mit Endpunkten fuer: POST /api/posts (erstellen), GET /api/posts/{id} (lesen), PUT /api/posts/{id} (aktualisieren), DELETE /api/posts/{id} (löschen). Alle Endpunkte müssen die TenantId des authentifizierten Benutzers berücksichtigen.

2.0 Post veröffentlichen SWR002

Ein Post kann über POST /api/posts/{id}/publish veröffentlicht werden. Dabei wird der Status auf PUBLISHED gesetzt und ein PostPublishedEvent erzeugt. Ein bereits veröffentlichter Post kann nicht erneut veröffentlicht werden.

3.0 Tenant-Isolation auf Datenebene SWR003

Jede Domain-Entity muss eine TenantId tragen. Datenbankabfragen müssen immer nach TenantId filtern. Ein Benutzer darf niemals Daten eines anderen Tenants sehen oder ändern.

Parent links: STK002 Multi-Tenancy

4.0 Übersetzung per KI (Author-getriggert) SWR004

Der Autor kann über POST /api/posts/{id}/translate eine KI-Übersetzung ausloesen. Das Ergebnis wird als Entwurf gespeichert und dem Autor zur Prüfung angezeigt. Erst nach expliziter Freigabe wird die Übersetzung übernommen.

5.0 Manuelle Übersetzung SWR005

Der Autor kann über PUT /api/posts/{id}/translation eine manuelle Übersetzung direkt eingeben und speichern.

Child links: SWA008 Translation als separates Aggregate mit eigenem Lifecycle

6.0 Audit-Trail für Posts SWR006

Jede Post-Entity muss createdAt, updatedAt, createdBy und updatedBy führen. Diese Felder werden automatisch beim Persistieren gesetzt.

Parent links: STK004 Audit-Fähigkeit

7.0 Rollenbasierte Zugriffskontrolle SWR007

Das System muss drei Rollen unterstützen: ADMIN, AUTHOR, READER. Nur AUTHOR und ADMIN duerfen Posts erstellen/bearbeiten. Nur ADMIN darf Tenants und Benutzer verwalten. READER hat nur Lesezugriff auf veröffentlichte Posts.

8.0 RSS/Atom Feed-Generierung SWR008

Das System muss bei Veröffentlichung eines Posts automatisch den RSS/Atom Feed aktualisieren. Feeds müssen nach Tags filterbar sein. Der Feed-Service konsumiert PostPublishedEvents via Kafka.

Domain Events (PostCreated, PostUpdated, PostPublished) müssen über Kafka publiziert werden. Jedes Event traegt EventMetadata mit ID, Timestamp, TenantId und CorrelationId.

14 Graceful Degradation bei KI-Ausfall SWR014

Bei Nichterreichbarkeit des KI-Providers (OpenRouter) muss das System eine aussagekräftige Fehlermeldung anzeigen. Alle nicht-KI-Funktionen müssen weiterhin uneingeschraenkt verfügbar sein.

15 Input-Validierung und OWASP-Schutz SWR015

Alle API-Eingaben müssen serverseitig validiert werden (Bean Validation). XSS-Schutz bei der Ausgabe von User-Content. CSRF-Schutz fuer zustandsbehaftete Endpunkte. SQL-Injection-Schutz durch Prepared Statements.

16 Custom Identity Provider mit OIDC SWR016

Das System muss einen eigenen Identity Provider Service bereitstellen. Dieser Service muss OpenID Connect (OIDC) Login unterstützen, sodass Benutzer sich über externe OIDC Provider (z.B. Google, GitHub) anmelden können. Der Service verwaltet Benutzerkonten, Rollen und Sessions.

17 Domain-basierte Tenant-Auswahl SWR017

Die Tenant-Zuordnung eines Requests muss über die verwendete Domain oder Subdomain erfolgen. Ein Tenant kann mehrere Domains und Subdomains konfigurieren (z.B. eigene Domain, Subdomain der Plattform). Das System muss die TenantId aus dem Host-Header des eingehenden Requests auflösen.

Parent links: STK002 Multi-Tenancy

Child links: SWA011 Domain-basierte Tenant-Resolution am Ingress

18 Automatisierte Kommentar-Moderation via LLM SWR018

Neue Kommentare müssen automatisiert durch ein LLM überprüft werden. Die Überprüfung nutzt das OpenRouter-Backend und bewertet Kommentare auf Spam, Beleidigungen und Off-Topic-Inhalte. Kommentare werden automatisch als approved, rejected oder review_pending klassifiziert. Bei LLM-Ausfall greift Graceful Degradation (Kommentar wird als review_pending markiert).

Parent links: STK001 Blog-Posts erstellen und veröffentlichen

Child links: SWA012 LLM-basierte Kommentar-Moderation als Adapter

19 Shadow-Banning für Kommentare SWR019

Das Kommentarsystem muss Shadow-Banning unterstützen. Ein shadow-gebannter Benutzer sieht seine eigenen Kommentare weiterhin normal, andere Benutzer sehen diese Kommentare jedoch nicht. Administratoren und Autoren können Shadow-Bans vergeben und aufheben.

Parent links: STK001 Blog-Posts erstellen und veröffentlichen

20 Tag CRUD API SWR020

Das System muss eine REST API für Tag-Verwaltung bereitstellen: POST /api/tags (Tag erstellen), GET /api/tags (alle Tags des Tenants), GET /api/tags/{id} (einzelnen Tag lesen), PUT /api/tags/{id} (Tag umbenennen), DELETE /api/tags/{id} (Tag löschen). Tag-Namen müssen pro Tenant eindeutig sein. Alle Endpunkte sind Tenant-scoped über den X-Tenant-Id Header.

21 Translation CRUD API SWR021

Das System muss eine REST API für die Verwaltung von Übersetzungen bereitstellen: POST /api/posts/{postId}/translations (Übersetzung erstellen), GET /api/posts/{postId}/translations (alle Übersetzungen eines Posts), GET /api/posts/{postId}/translations/{id} (einzelne Übersetzung lesen), PUT /api/posts/{postId}/translations/{id} (Übersetzung aktualisieren), POST /api/posts/{postId}/translations/{id}/approve (Übersetzung freigeben), POST /api/posts/{postId}/translations/{id}/reject (Übersetzung ablehnen), DELETE /api/posts/{postId}/translations/{id} (Übersetzung löschen). Alle Endpunkte sind Tenant-scoped über den X-Tenant-Id Header.

22 Time-based Auto Publishing SWR022

Das System muss zeitgesteuerte Veröffentlichung (Scheduled Publishing) unterstützen:

  • Ein Post kann mit einem zukünftigen Veröffentlichungszeitpunkt (publishAt) versehen werden.
  • Ein Scheduler prüft periodisch, ob Posts zur Veröffentlichung anstehen.
  • Zum geplanten Zeitpunkt wird der Post automatisch in den Status PUBLISHED überführt.
  • Ein PostPublishedEvent wird dabei ausgelöst (wie bei manueller Veröffentlichung).
  • Der Autor kann den geplanten Zeitpunkt bis zur Veröffentlichung ändern oder stornieren.
  • Die REST API wird um das Feld publishAt erweitert (optional bei POST/PUT /api/posts/{id}).

Parent links: STK013 Zeitgesteuerte Veröffentlichung
