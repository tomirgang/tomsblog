= 8. Querschnittliche Konzepte
:sectnums:

== Multi-Tenancy

Die Multi-Tenancy-Fähigkeit setzt die Stakeholder-Anforderung STK-002 um und wird durch SWR-003 (Tenant-Isolation auf Datenebene) detailliert.

Jede Domain-Entity trägt eine `TenantId`. Die Tenant-Zuordnung eines Requests erfolgt über die verwendete Domain (SWR-017, SWA-011): Der Host-Header wird am Ingress in eine TenantId aufgelöst und als `X-Tenant-Id` an Backend-Services propagiert. Ein Tenant kann mehrere Domains besitzen. Tenant-Isolation wird auf Datenbank-Ebene sichergestellt (Row-Level-Security oder Schema-basiert, noch zu entscheiden).

== Database per Service

Jeder Microservice besitzt seine eigene, dedizierte Datenbank-Instanz (SWA-015, ADR-0019). Die Technologiewahl (PostgreSQL oder MongoDB) erfolgt pro Service anhand des Datenmodells. Kein Service darf direkt auf die Datenbank eines anderen Services zugreifen.

* Blog Content Service: PostgreSQL (relationale Daten, Flyway-Migrationen)
* Auth Service: PostgreSQL (User/Role-Management)
* Service-übergreifender Datenzugriff ausschließlich über gRPC (SWA-009) oder Domain Events (SWA-005)
* Lokale Entwicklung: dedizierte Datenbank-Container pro Service
* Kubernetes: CloudNativePG Operator (PostgreSQL), MongoDB Community Operator

== Audit

Das Audit-Konzept erfüllt die Anforderungen STK-004 (Audit-Fähigkeit) und SWR-006 (Audit-Trail für Posts).

Alle persistierten Entities implementieren das `Auditable`-Interface:

* `createdAt` / `updatedAt` (automatisch gesetzt)
* `createdBy` / `updatedBy` (aus Security Context)

== Domain Events

Domain Events bilden die Grundlage für die serviceübergreifende Kommunikation (SWR-009) und werden über Kafka als zentralen Event-Broker (SWA-005) verteilt. Die Event-Contracts sind als geteilte Library (SWA-003) definiert.

* Events werden im Aggregate gesammelt (`AggregateRoot.registerEvent()`)
* Nach erfolgreicher Persistierung werden sie über Kafka publiziert
* Event-Contracts als geteilte Library (`libs/event-contracts`) (SWA-003)
* Jedes Event trägt `EventMetadata` (ID, Timestamp, TenantId, CorrelationId)

== Task-Queues (RabbitMQ)

Für Job-Verteilung und asynchrone Arbeitsaufträge wird RabbitMQ eingesetzt. Die Trennung von Event-Streaming (Kafka) und Task-Queues (RabbitMQ) folgt ADR-0018.

* Übersetzungsaufträge, TTS-Generierung, Snapshot-Erstellung, Benachrichtigungen
* Work-Queue-Pattern: konkurrierende Consumer verarbeiten Jobs fair
* Dead-Letter-Exchanges für fehlgeschlagene Nachrichten
* Quorum Queues für Durability und Hochverfügbarkeit
* Request/Reply-Pattern für synchrone Interaktion über Messages

== Synchrone Service-Kommunikation

Für synchrone Aufrufe zwischen Microservices wird gRPC eingesetzt (SWA-009). Die asynchrone Kommunikation teilt sich in Event-Streaming (Kafka) und Task-Queues (RabbitMQ) auf (ADR-0018). Die Aufteilung erlaubt lose Kopplung bei Events, zuverlässige Job-Verteilung bei Tasks und typsichere, performante Abfragen zwischen Services.

* Service-Interfaces werden als `.proto`-Dateien in einer geteilten Library definiert
* Protobuf sorgt für typsichere Contracts und effizientes Binary-Protokoll
* Streaming-Unterstützung für größere Datenmengen

== Error Handling

* Domain-Exceptions für fachliche Fehler
* Globaler Exception Handler im REST-Adapter (Problem Details RFC 9457)
* Keine Framework-Exceptions in der Domain-Schicht

== Internationalisierung

Die Mehrsprachigkeit setzt STK-003 um. Übersetzungen können manuell (SWR-005) oder KI-gestützt (SWR-004) erstellt werden, wobei das Translation-Aggregate einen eigenen Lifecycle besitzt (SWA-008). Bei KI-Ausfällen greift Graceful Degradation (SWR-014).

* Blog-Posts werden pro Locale gespeichert
* Ein Post hat eine Haupt-Locale und optionale Übersetzungen
* Übersetzungen werden vom Autor über die UI ausgelöst (nicht automatisch)
* KI-gestützte Übersetzung: Autor startet Anfrage, AI Service liefert Vorschlag, Autor prüft und übernimmt (SWR-004, SWA-006)
* Manuelle Übersetzung: Autor gibt Übersetzung direkt ein (SWR-005)
* Kein automatisches Übersetzen bei Veröffentlichung; der Autor behält die volle Kontrolle

== Security

Die Sicherheitsanforderungen leiten sich aus STK-012 (Sicherheit) und STK-005 (Benutzerverwaltung) ab. SWR-015 definiert die Input-Validierung und den OWASP-Schutz, SWR-007 die rollenbasierte Zugriffskontrolle.

* Authentication über eigenen Auth Service mit OIDC-Unterstützung (SWR-016, SWA-010)
* RBAC: Admin, Autor, Leser (SWR-007)
* JWT-basierte Token-Validierung in allen Services (Public Key lokal)
* OWASP Top 10 wird bei Code-Reviews geprüft (SWR-015)
* Input-Validierung an den Systemgrenzen (SWR-015)

== Session Management

Für die horizontale Skalierbarkeit des Blog Content Service (STK-045) werden HTTP-Sessions extern in Redis gespeichert (SWR-057, SWA-032, ADR-0030). Dies ermöglicht den Betrieb mehrerer Replicas (SWR-058) und unterbrechungsfreie Rolling Updates.

* Spring Session Data Redis als Implementierung (Auto-Configuration über Dependency und YAML)
* Redis als Single-Instance Deployment im Namespace `redis` (INF-014)
* Session-Daten: Spring Security Authentication (OIDC/formbasiert), Benutzerrollen, SuperAdmin Tenant-Auswahl (SWR-053)
* Session-Timeout: 30 Minuten (Spring Default)
* Keine Redis-Persistenz (Sessions sind kurzlebig und reproduzierbar)
* Passwort-Authentifizierung über Kubernetes Secret
* Linkerd mTLS zwischen Blog-Pod und Redis (ADR-0021)
* Network Policy beschränkt Redis-Zugriff auf den `tomsblog` Namespace

== E2E-Testing

Die End-to-End-Testing-Strategie setzt STK-052 um und stellt sicher, dass alle relevanten UI-Use-Cases durch Browser-basierte Selenium-Tests verifiziert werden. Die Architekturentscheidungen sind in ADR-0033 dokumentiert, die technische Umsetzung in SWA-035 beschrieben.

* Separates Maven-Modul `e2e-tests/` mit eigenem Profil (`-Pe2e`)
* Selenium WebDriver mit Testcontainers-Selenium (Chrome-Container)
* Page Object Model (POM) für wartbare Seiten-Abstraktionen
* JUnit 5 Extension für automatische Screenshots bei Fehlschlag
* 16 Testszenarien über 5 Testklassen: öffentliche Blog-Ansichten (SWR-079), Autoren-Workflows (SWR-080), Authentifizierung (SWR-081), Admin-Workflows (SWR-082), SuperAdmin-Verwaltung (SWR-083)
* Lokale Ausführung: `./mvnw verify -Pe2e` (Docker erforderlich)
* CI/CD: separater GitHub Actions Job mit Screenshot-Artefakten
* Release-Pflicht: E2E-Tests sind Voraussetzung für ein Release (SWR-078)
