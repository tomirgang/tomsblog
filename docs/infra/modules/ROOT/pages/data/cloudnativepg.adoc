== Cluster-Definition

PostgreSQL wird über den CloudNativePG Operator als Kubernetes Custom Resource verwaltet (INF-005, SWA-018, ADR-0023). Die Cluster-Definition liegt unter `infra/k8s/postgres/`.

=== Aktuelle Konfiguration

[cols="1,2"]
|===
| Parameter | Wert

| Instanzen | 1 (Single Instance, kein Failover)
| Storage | 10 Gi (hcloud-volumes)
| shared_buffers | 128 MB
| effective_cache_size | 256 MB
| Memory | 384 Mi Request / 768 Mi Limit
| CPU | 200m Request / 500m Limit
| Namespace | postgres
| Service-Endpunkt | postgres-cluster-rw.postgres.svc.cluster.local:5432
|===

== Failover

Bei Ausfall der Primary-Instanz übernimmt die Replica automatisch. Der Operator:

1. Erkennt den Ausfall (Health-Check fehlgeschlagen)
2. Promoted die Replica zur neuen Primary
3. Aktualisiert den `-rw`-Service-Endpunkt
4. Startet eine neue Replica (wenn Node verfügbar)

[mermaid]
----
sequenceDiagram
    participant OP as CloudNativePG Operator
    participant P as Primary Pod
    participant R as Replica Pod
    participant SVC as Service (postgres-cluster-rw)

    Note over P: Pod Failure
    OP->>OP: Health-Check schlägt fehl
    OP->>R: Promote to Primary
    OP->>SVC: Update Endpoint → Replica
    Note over R: Neue Primary
    OP->>OP: Erstelle neue Replica
----

== Datenbanken

Der Cluster folgt dem Database-per-Service-Pattern (ADR-0019). Die Datenbanken werden deklarativ als eigenständige CloudNativePG Database-Ressourcen (CRD) verwaltet (ADR-0029, INF-013, SWA-030). Die Manifeste liegen unter `infra/k8s/postgres/databases.yaml`.

[cols="1,2,1"]
|===
| Datenbank | Service | Owner

| blog_content | blog-content | app (Database CRD)
| user_management | user-management | app (Database CRD)
| tenant_management | tenant-management | app (Database CRD)
|===

Die `initdb`-Konfiguration erstellt nur noch eine neutrale Platzhalter-Datenbank (`app`). Alle Service-Datenbanken werden über die Database CRD verwaltet:

[source,yaml]
----
bootstrap:
  initdb:
    database: app
    owner: app
----

Jede Service-Datenbank ist als eigenständige Kubernetes-Ressource definiert:

[source,yaml]
----
apiVersion: postgresql.cnpg.io/v1
kind: Database
metadata:
  name: blog-content-db
  namespace: postgres
spec:
  name: blog_content
  owner: app
  databaseReclaimPolicy: retain
  cluster:
    name: postgres-cluster
----

Der Operator reconciliert den Zustand und meldet Fehler im `.status`-Feld. Die `databaseReclaimPolicy: retain` verhindert versehentlichen Datenverlust beim Löschen der Ressource.

== Credentials

Die Datenbank-Credentials werden vom Operator automatisch als Kubernetes Secret erstellt:

[cols="1,2"]
|===
| Secret | Inhalt

| postgres-cluster-app | username, password (für Application User)
| postgres-cluster-superuser | username, password (für Admin-Zugang)
|===

Alle drei Services (blog-content, user-management und tenant-management) referenzieren das `postgres-cluster-app` Secret in ihrer Deployment-Konfiguration.

== Verbindung zum App-Repository

Die Cluster-Definition referenziert die Secrets aus dem App-Repository. Der Reflector-Operator synchronisiert das App-Secret in den `tomsblog`-Namespace, damit der blog-content Service darauf zugreifen kann.
