= Netzwerk & DNS
:sectnums:

== Netzwerk-Topologie

Das Cluster-Netzwerk nutzt Flannel als CNI (k3s-Standard) mit einem privaten Hetzner-Netzwerk (10.0.0.0/16). Der externe Zugang erfolgt über einen Hetzner Load Balancer, der automatisch durch den Hetzner CCM bereitgestellt wird (Traefik LoadBalancer-Service).

[mermaid]
----
graph TB
    DNS[DNS: blog.tomirgang.de] --> LB[Hetzner LB<br/>Port 80, 443]
    LB --> N2[Worker 1<br/>CPX22]
    LB --> N3[Worker 2<br/>CPX22]
    N1[Controller<br/>CPX22] ---|Privates Netzwerk| N2
    N2 ---|Privates Netzwerk| N3
    N1 ---|Privates Netzwerk| N3
----

== DNS-Konfiguration

Die DNS-Einträge werden manuell beim Domain-Provider konfiguriert:

[cols="1,1,2"]
|===
| Record | Typ | Ziel

| blog.tomirgang.de | A | Hetzner LB IP (öffentlich)
| cluster.tomirgang.de | A | Controller IP (nur für kubectl-Zugang)
|===

== Load Balancer

Der Hetzner Load Balancer wird automatisch durch den Hetzner CCM erstellt, wenn Traefik als LoadBalancer-Service deployed wird. Er terminiert keine TLS-Verbindungen (TLS-Passthrough). Die TLS-Terminierung erfolgt durch Traefik im Cluster.

[cols="1,1,1"]
|===
| LB-Port | Ziel-Port | Protokoll

| 80 | 80 | TCP (HTTP, für ACME + Redirect)
| 443 | 443 | TCP (HTTPS, TLS-Passthrough)
|===

Der Kubernetes-API-Zugang (Port 6443) erfolgt direkt über die öffentliche IP des Controllers, nicht über den Load Balancer.

== Intra-Cluster-Kommunikation

Innerhalb des Clusters wird die gesamte Pod-zu-Pod-Kommunikation durch Linkerd mTLS verschlüsselt (INF-006). Details dazu in xref:../service-mesh/mtls.adoc[mTLS].

Der Node-zu-Node-Traffic im privaten Hetzner-Netzwerk ist nicht zusätzlich verschlüsselt (kein WireGuard). Die Sicherheit wird durch die Netzwerk-Isolation des privaten Netzwerks und Linkerd mTLS auf Applikationsebene gewährleistet.
