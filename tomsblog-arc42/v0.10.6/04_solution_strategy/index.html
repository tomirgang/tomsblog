4. Lösungsstrategie

1. Architekturansatz

Die zentralen Architekturentscheidungen setzen die Stakeholder-Anforderungen an Erweiterbarkeit (STK-009), Multi-Tenancy (STK-002) und Audit-Fähigkeit (STK-004) um:

Entscheidung Begründung Anforderungen

Hexagonale Architektur

Framework-unabhängige Domain, austauschbare Adapter

SWA-001

Microservices

Unabhängige Deployments, Technologie-Heterogenität (REST + GraphQL)

STK-009

Event-Driven (Kafka + RabbitMQ)

Kafka: Event-Streaming, Replay, Audit-Trail; RabbitMQ: Task-Queues, Job-Verteilung

SWA-005, SWR-009

gRPC (synchron)

Typsichere Service-Contracts, effizientes Binary-Protokoll

SWA-009

Multi-Tenant

Mandantenfähigkeit von Anfang an im Design

STK-002, SWR-003

Database per Service

Eigene DB-Instanz pro Service, Technologiewahl (PostgreSQL/MongoDB) pro Service

SWA-015

3. Qualitätsstrategien

  • Testbarkeit: Domain ohne Framework-Abhängigkeiten → Pure Unit Tests

  • Nachvollziehbarkeit: Audit-Felder in allen Entities, Requirement Tracing

  • Beobachtbarkeit: Prometheus + Grafana + Loki + Tempo von Anfang an

  • Inkrementell: Meilenstein-basierter Ausbau (Text-Blog → Kommentare → SPA → Podcast → Video)
