Das Detail Design des Blog Content Service mit Klassendiagrammen und Ablaufbeschreibungen ist in der Software Detail Design Dokumentation beschrieben.

2.1. Domain Layer (domain/)

Reine Java-Klassen ohne Framework-Abhaengigkeiten. Die gemeinsamen Domain Primitives (EntityId, TenantId, AuthorId, AggregateRoot, DomainEvent, Auditable) werden über das Shared Kernel (SWA-002) als Framework-freie Library bereitgestellt.

Baustein Typ Beschreibung

Post

Aggregate Root

Titel, Slug, Content, ContentType (HTML/MARKDOWN), Status, Locale, AuthorId (Referenz), TagIds, Sources, Attachments. Registriert Domain Events.

ContentType

Enum

HTML, MARKDOWN. Steuert die Rendering-Logik fuer die Anzeige (SWR-035, SWA-027).

Translation

Aggregate Root

Uebersetzung eines Posts mit eigenem Lifecycle (DRAFT/REVIEW_PENDING/APPROVED/REJECTED).

Tag

Entity

TagId, TenantId, name, slug. Tenant-scoped mit eigener Identitaet.

PostId, TagId, TranslationId, AttachmentId

Value Objects

Typsichere IDs (Records)

Slug, PostLocale

Value Objects

Validierung im Konstruktor

Source

Value Object

Quellenreferenz: URL + Titel

Attachment

Value Object

AttachmentId, filename, contentType, size, show, storageKey. show=true fuer angezeigte, show=false fuer eingebettete Inhalte.

PostStatus

Enum

DRAFT, PUBLISHED, ARCHIVED

TranslationStatus

Enum

DRAFT, REVIEW_PENDING, APPROVED, REJECTED

TranslationSource

Enum

MANUAL, AI_GENERATED

PostCreatedEvent, PostPublishedEvent, PostUpdatedEvent

Domain Events

Post-Lifecycle-Events

TranslationCreatedEvent, TranslationApprovedEvent

Domain Events

Translation-Lifecycle-Events
AuthorId liegt im shared-kernel (SWA-002). Der blog-content Service haelt keine Author-Stammdaten vor (werden vom Auth-Service in Phase 3 bereitgestellt).

2.4. Datenbank-Migrationen (Flyway)

Die Datenbank-Schema-Verwaltung erfolgt über Flyway (SWA-013). Alle Migrationen liegen unter src/main/resources/db/migration/ und werden beim Service-Start automatisch ausgefuehrt. Hibernate validiert das Schema gegen die Entity-Klassen (ddl-auto: validate).

Migration Beschreibung

V1__create_posts_schema.sql

posts, post_tags, post_sources, post_attachments

V2__create_tags_schema.sql

tags mit Unique-Index auf (tenant_id, name) und (tenant_id, slug)

V3__create_translations_schema.sql

translations mit FK auf posts, Unique auf (post_id, locale)

V4__add_content_type_to_posts.sql

content_type VARCHAR(20) NOT NULL DEFAULT 'HTML' (SWR-035, SWA-027)

V5__add_fulltext_search_index.sql

GIN-Index fuer Volltextsuche ueber title und content mit tsvector (SWR-038)

V6__add_series_navigation.sql

Optionale Serien-Navigationsfelder series_previous_post_id und series_next_post_id (SWR-040)

V7__add_featured_fields.sql

Optionale Featured-Felder featured_from und featured_until (SWR-041)

V8__create_audit_log.sql

Audit-Log-Tabelle mit Indizes auf tenant_id und timestamp (SWR-056, SWA-031)
Weitere Services werden analog strukturiert. Details werden ergänzt, sobald sie implementiert sind.

3. Shared UI Library (libs/shared-ui)

Die Shared UI Library (SWR-065, SWR-066, SWR-067, SWR-068, SWA-033) stellt gemeinsame Thymeleaf-Templates und CSS-Styles bereit, die von allen Services mit Web-UI verwendet werden. Analog zum Shared Kernel (SWA-002) vermeidet sie Code-Duplikation und stellt ein einheitliches Look-and-Feel sicher (STK-048).

Baustein Beschreibung

templates/shared/layout/default.html

Master-Layout: HTML-Grundstruktur mit Pico CSS, Header-/Content-/Footer-Bereiche via Thymeleaf Layout Dialect

templates/shared/fragments/footer.html

Einheitlicher Footer: Copyright, Impressum-Link, Datenschutz-Link, Versionsnummer

static/css/custom.css

Plattformweite CSS-Anpassungen: Sticky-Footer-Layout, Tenant-Branding-Hooks (CSS Custom Properties)
Header-Fragmente verbleiben in den jeweiligen Services, da sie service-spezifische Navigation enthalten (z.B. Blog-Navigation im Blog Content Service, Auth-Menü im User Management Service). Das gemeinsame Layout bindet den Header über einen service-lokalen Fragment-Verweis ein.

4. Ebene 2: User Management Service

Der User Management Service verwaltet plattformspezifische Benutzerprofile, Rollen und Tenant-Zuordnungen (SWR-043, SWA-029). Er agiert als Ergänzung zum externen OIDC Provider Authentik (ADR-0027, SWR-016). Authentik übernimmt Authentifizierung (Login, MFA, Passwort-Policies), während der User Management Service die Autorisierungsdaten (Rollen, Tenant-Mitgliedschaften) intern verwaltet.

4.1. Domain Layer (domain/)

Baustein Typ Beschreibung

UserProfile

Aggregate Root

OidcSubject (eindeutige OIDC-Kennung), Username, PasswordHash, AuthSource, E-Mail, DisplayName, ApprovalStatus (PENDING/APPROVED/REJECTED), Rollen, TenantMemberships. Synchronisiert sich aus OIDC-Claims oder internem Login.

TenantSettings

Entity

TenantId, LoginMode, autoApproveOidc, autoApproveEmailDomains. Konfiguriert Login-Verhalten und Auto-Approval pro Tenant (SWR-044, SWR-045).

Role

Enum

SUPERADMIN, ADMIN, AUTHOR, REVIEWER, READER (SWR-007). SUPERADMIN wird ueber Infrastruktur-Konfiguration angelegt.

AuthSource

Enum

INTERNAL, OIDC. Gibt an, ob der Benutzer ueber internes Konto oder OIDC authentifiziert wird.

ApprovalStatus

Enum

PENDING, APPROVED, REJECTED. Status der Benutzerfreigabe (STK028).

LoginMode

Enum

INTERNAL, OIDC, BOTH. Konfigurierbare Login-Methode pro Tenant (SWR-044).

TenantMembership

Value Object

TenantId + Role. Ein Benutzer kann in verschiedenen Tenants unterschiedliche Rollen haben.

UserProfileId

Value Object

Typsichere ID (Record)

5. Ebene 2: Tenant Management Service

Der Tenant Management Service verwaltet den Tenant-Lifecycle und die Tenant-Konfiguration (SWR-072, SWA-034, ADR-0031). Er uebernimmt die Verantwortlichkeiten, die bisher im User Management Service als TenantSettings modelliert waren, als eigenstaendiger Bounded Context.

Das Detail Design des Tenant Management Service ist in der Software Detail Design Dokumentation beschrieben.

5.1. Domain Layer (domain/)

Baustein Typ Beschreibung

Tenant

Aggregate Root

TenantId, slug, displayName, tagline, TenantStatus, LoginMode, Auto-Approval-Konfiguration, OIDC-Provider-Config, Impressum, Datenschutzerklaerung. Lifecycle-Management mit Statusuebergaengen.

TenantStatus

Enum

ACTIVE, SUSPENDED, DEACTIVATED. Steuert die Verfuegbarkeit des Tenants.

LoginMode

Enum

INTERNAL, OIDC, BOTH. Konfigurierbare Login-Methode pro Tenant (migriert aus user-management).
